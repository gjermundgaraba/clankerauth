# 0.26.0 — Breaking: the SDK verifier keeps what it reads in a store, and runs on Cloudflare Workers

The SDK's verifier no longer shares a running read between verifications. What it has read and
checked lives in a store of plain values, which a process makes once; a verifier acquired per
request reads the issuer in that request when the store holds nothing current, and writes the
result back. Its reads no longer use `redirect: "error"`, which Cloudflare Workers rejects. The
issuer's endpoints, its errors, the database, the administration contract, the command and
effect-actions are as in 0.25.0, so a 0.25 issuer serves a 0.26 resource server unchanged, and
the reverse. Every package and the server go to 0.26.0 to keep one version across the release.

## Upgrading

1. **Make a store, once, and pass it.** `Verifier.make` and a declared resource's `layer` take
   `store`, which is required:

   | 0.25                                     | 0.26                                                                     |
   | ---------------------------------------- | ------------------------------------------------------------------------ |
   | `Verifier.make({ issuer, resource, … })` | `Verifier.make({ issuer, resource, store, … })`                          |
   | `Notes.layer({ issuer, publicUrl, … })`  | `Notes.layer({ issuer, publicUrl, store, … })`                           |
   | a verifier acquired once and shared      | `const store = Verifier.store()` at module scope; a verifier per request |

   Make the store where the process starts, `const store = Verifier.store()` at module scope,
   and give every verifier and resource of the process the same one: it is keyed by issuer and
   resource. A store made per request still verifies correctly, but reads the issuer on every
   request.

2. **On Cloudflare Workers, acquire the verifier in each request.** A Worker's I/O belongs to
   the request that started it: a request cannot resume work another one started, and since the
   2024-10-14 compatibility date a continuation whose request has ended is dropped
   ([I/O on behalf of a different request](https://developers.cloudflare.com/workers/observability/errors/#cannot-perform-io-on-behalf-of-a-different-request),
   [cross-request promise resolution](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#handle-cross-request-promise-resolution-correctly)).
   0.25's verifier cached each read as one running Effect, which concurrent verifications
   joined, so a verifier kept across requests made one request wait on I/O another owned: most
   requests of a burst hung until the runtime cancelled them. Keep the store at module scope, as
   data, and make the verifier, or build the resource's layer, in the request. A verifier holds
   no running work now, so on Node acquiring it once is just as correct.

3. **A redirect is an outage.** Reads are sent with `redirect: "manual"`, and a document
   answered with any 3xx fails as `ProviderUnavailable` with operation `http.redirect`, as 0.25
   failed it with `http.request`. Point `issuer` at the issuer itself, not at an address that
   redirects to it.

## SDK

- New `Verifier.store()` and its `Verifier.Store`: each issuer's JWKS keys and each resource's
  verified key list, with when each was read and when it expires, and the outcome of the last
  read, which holds off the next. It holds values only, never an Effect, fiber, Promise,
  `Response` or timer.
- A verifier on a hit verifies locally; on a miss or once what the store holds has expired, it
  reads in the verification that missed, under the same deadlines (three seconds for a key list,
  five for a resource's whole verification), and writes the result back. Concurrent misses
  each read, and none waits on another's: steady traffic costs one or two more issuer reads per
  refresh than 0.25, and a burst arriving at an empty or expired store reads once per
  verification in it. An abandoned read writes nothing, and a read that ends after a newer
  one leaves the newer outcome standing.
- Every rule is as in 0.25: signature, issuer, audience, `typ`, expiry and scopes; a JWKS
  document answers for a minute, a key list is read again after a minute and at most every five
  seconds, a failed read holds off the next for five seconds, and a held list decides through
  an outage until it expires. The warning that key list reads are failing, and the note that
  they have recovered, are logged once per outage for each resource in the store, not once per
  verifier.
- Reads use `redirect: "manual"` instead of `"error"`, which Cloudflare Workers rejects before
  sending ([Request](https://developers.cloudflare.com/workers/runtime-apis/request/#options)), and
  fail on any 3xx; they still follow none.

## Issuer, dashboard, command and administration contract

- Unchanged. The issuer builds its administration verifier over a store of its own.
