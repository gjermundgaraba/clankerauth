# 0.26.1 — A key list read gives its JWKS fetch its own three seconds

The SDK verifier's key list read used one three-second deadline for two fetches in a row: the list POST and, when the store held no current JWKS, the JWKS fetch inside its verification. On a freshly started isolate each fetch can take a second or more, so a cold burst of verifications ran both into the one budget and reported `key-list.timeout` for reads that would have succeeded. Now the list POST and the JWKS fetch each get `listReadTimeout` (three seconds) of their own; the header is still refused before any JWKS read, local verification runs outside both deadlines, and a JWKS fetch that times out is recorded on the key list as `jwks.timeout` with the usual five-second cooldown while a held list keeps deciding. The issuer, its endpoints, the database, the administration contract and the SDK's API are as in 0.26.0. Every package and the server go to 0.26.1 to keep one version across the release.

One case is slower than before: an issuer that answers the list late and then stalls on the JWKS is now cut off by the request's own five-second deadline (`verify.timeout`) instead of the three second list deadline, so a held list does not decide it. An issuer that stops answering altogether still costs three seconds and is still decided by the held list.
