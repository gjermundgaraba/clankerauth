# 0.26.2 — A key list read runs its two fetches together

0.26.1 gave a key list read's list POST and its JWKS fetch three seconds each, one after the other, so an issuer that answered the list late and then stalled on the JWKS was cut off by the request's own five-second deadline (`verify.timeout`) and a held list did not decide it. Since both documents last a minute, a list refresh usually brings a JWKS miss with it. Now the read starts the JWKS fetch beside the list POST, each still on `listReadTimeout` (three seconds) of its own, so a read ends within three seconds whatever stalls, and a held list decides any read that fails. The header is still refused before the JWKS is used, a JWKS already held is not fetched, and a JWKS fetch that times out is still recorded on the key list as `jwks.timeout` with the usual five-second cooldown. A key list read that misses the JWKS now starts that fetch even when the list POST fails.

The issuer now mints its signing key when it starts, if it has none. Before, the first signature or JWKS read minted it, and two at once minted two keys: a fresh issuer's first key list and a JWKS read beside it could disagree on the key, and a resource server would refuse every key for a minute. One window remains under immediate-use rotation: a list signed by a key minted after a read's JWKS fetch began fails verification until the next JWKS read, the same window the SDK already accepts while a JWKS is held, and the held list keeps deciding. The issuer's endpoints, the database, the administration contract and the SDK's API are as in 0.26.1. Every package and the server go to 0.26.2 to keep one version across the release.
