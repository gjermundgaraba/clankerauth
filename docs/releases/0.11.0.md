# 0.11.0 — offline API keys

Breaking for the server, the SDK and the development package. Resource servers verify
API keys offline, against a signed key list per resource, instead of asking the issuer
on every request. The online verification endpoint is gone, so an SDK before 0.11.0
cannot verify keys against this issuer; upgrade both together.

## Upgrade

Existing keys keep working and need no reissue: the key list is built from the digests
the issuer already stores. Nothing is migrated.

## Issuer

- `POST /api/issuer/verifyApiKey` is replaced by `POST /api/issuer/keyList`, which takes
  `{ resource }` and needs no credential. It answers `{ list }`: a JWT with header
  `typ: key-list+jwt`, signed with the access-token key and published in the same JWKS,
  whose `aud` is the resource and whose `keys` claim holds one sealed entry per enabled,
  unexpired key granted on it.
- An entry is found by, and sealed under, values derived from the key's SHA-256 digest
  and the resource identifier. Only a holder of the key can find or open it: its key ID,
  owner ID, the scopes it still has on the resource, and its expiry. Anyone else still
  sees how many entries the resource has, when they come and go, and roughly how large
  each grant is.
- An unknown resource and the administration resource get a list with no entries.
- A list is valid for 24 hours from `iat`. That is how long a resource server that
  cannot reach the issuer keeps accepting the keys it last saw, and so the longest a
  revoked key stays usable during an outage.
- The API-key plugin's per-key rate limit is off; nothing counts key use any more.
  Rate limiting is the resource server's.
- A key whose stored row no longer decodes is left out of every key list and logged,
  instead of failing the list for every resource.
- The dashboard states the revocation delay beside the API keys.

## SDK

- `Verifier`, `Resource.admit`, `Resource.middleware` and `authorize` verify keys
  offline. One key-list read answers every key for a minute, so disabling, deleting,
  re-scoping or expiring a key takes effect within about a minute. A failed read, or one
  that takes longer than three seconds, is no error while the last list is inside its
  24 hours; past them, or before any list has
  been read, a key is `ProviderUnavailable`. Reads that start failing are logged once as
  a warning, and their recovery once at info level.
- `Principal.expiresAt` is a key's own expiry, where it has one, instead of always
  `undefined`.
- `Resource.watch(authorization, access)` holds a connection admitted with a credential,
  such as a WebSocket, to that credential: it fails with the first refusal once a token
  expires or a key is revoked, expires or loses the scope. Race it against the
  connection.
- `RateLimited` is removed from `/errors` and from `authenticationErrors`: nothing
  produces it. `admit` no longer renders `429` or `Retry-After`.
- The signing fake issuer moves from `@gjermundgaraba/clankerauth-dev/testing` to
  `@gjermundgaraba/clankerauth-sdk/testing`, beside the verifier it stands in for.
  `apiKey(permissions, expiresAt)` takes permissions as the real issuer does, resource
  identifier to scopes, so one key can reach several resources; both default to every
  configured scope on the configured resource, never expiring. `verifications()` is
  replaced by `keyLists()`, and `revoke(key)` leaves the key out of the next list.
- `…/clankerauth-sdk/key-list` exports the list format: `digest`, `seal`, `open`, the
  `type`, the `lifetime` and the entry, grant and claim schemas. Resource servers need none of it; it is
  for issuers, such as test fakes.

## Development package

- The disposable issuer serves key lists as the server does.
- The `/testing` entry is removed; the fake issuer is now the SDK's.
