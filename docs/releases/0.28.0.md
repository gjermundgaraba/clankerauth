# 0.28.0 — Administration keys

Nothing to upgrade. Administration now accepts an API key, so a program with no browser and no
disk to keep a sign-in on, such as a deployer, administers an issuer unattended. No existing key
gains access: issuers before 0.28.0 refused administration grants, so a key administers only once
the owner grants it there. The database, the configuration, the SDK's API and every other
endpoint are as in 0.27.0, so an application on SDK 0.27.0 verifies against a 0.28.0 issuer and
the reverse. Every package and the server go to 0.28.0 to keep one version across the release.

## Issuer

- An **administration key** is an API key granted `clankerauth:read`, `clankerauth:write` or
  both on the built-in administration resource, `<CLANKERAUTH_BASE_URL>/`. Creating and editing
  a key accepts that grant, which was refused before; any other scope on that resource is still
  refused, `offline_access` among them.
- `/api/owner/<action>` and `/mcp` take an administration key as their bearer, as they take the
  owner's access token. `clankerauth:read` lists and `clankerauth:write` allows every action, as
  for a token. A key without either administration scope is refused with `Unauthenticated`
  (401), and a read-only key calling a change with `Forbidden` (403).
- The issuer checks an administration key's grant on administration in its own database on
  every request: disabling, deleting, re-scoping or expiring the key ends administration on the
  next request. That grant never enters a key list, so the administration resource's key list
  stays empty; the key's grants on other resources are listed, and apply, as any key's.
- An administration key acts as the owner. With `clankerauth:write` it may create, re-scope and
  delete keys, administration keys among them and itself; `clankerauth:write` already amounts to
  access to every resource. It cannot sign in to the dashboard or call the dashboard's cookie
  binding, `/api/<action>`.

## Dashboard

- The API-key form offers the clankerauth administration resource beside the others.

## CLI

- With `CLANKERAUTH_TOKEN` set, administration commands send that key instead of the owner's
  sign-in, at the issuer `CLANKERAUTH_URL` names, which they then require. No sign-in is read or
  written, so the command runs in a container. The owner creates the key once, signed in:

  ```sh
  clankerauth create-api-key --name deployer --expires-at null \
    --permissions '{"https://clankerauth.home.example/":["clankerauth:read","clankerauth:write"]}'
  ```

## SDK and administration contract

- Unchanged in code. A program calling `OwnerHttp` passes the key to `authorizing` or `token` of
  `/credentials` as `token: Config.Redacted("CLANKERAUTH_TOKEN")`; it is sent instead of the
  owner's sign-in whenever the variable is set. Without `token`, nothing is read from the
  environment.
