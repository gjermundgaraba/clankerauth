# 0.10.0 — consent-gated clients and read-only administration

Breaking for the server and the development package, which embeds it. The SDK is
unchanged; it moves to 0.10.0 only because both npm packages share one version.

## Upgrade

The first start clears stored authorization once: consents, access and refresh tokens,
and pending authorization codes. Clients, resources and API keys are untouched. Every
client then authorizes once more; for administration MCP, give `clankerauth:read`
alone wherever read-only access is enough.

Earlier versions kept consents and tokens when the owner removed a resource from a
client, and only the provider's per-client check kept them from working. That check
is now off, so a kept refresh token would work again. The same step removes the links
earlier versions gave automatic clients, which no longer have any. It runs in one
transaction and records itself in SQLite's `user_version`, so it runs once, and again
only on a database restored from an earlier version. Downgrading is unsupported: a
database that ran this step is not upgraded again.

## Clients and client access

- Client access applies to managed clients only, which skip consent. An automatic
  (DCR or CIMD) client may ask for any resource, including ones added later, and
  consent decides. The provider's `enforcePerClientResources` is off; the issuer's
  own check refuses a managed client a resource outside its access, at
  authorization and at consent.
- That refusal is the issuer's JSON `400` with `invalid_target` and
  `Client access is required`, not an error redirect to the client, including for
  `prompt=none`. A request with `prompt=consent` reaches the consent screen first,
  and approving it is refused.
- `setClientAccess` refuses automatic clients with `BadRequest`. Removing a resource
  from a managed client's access revokes its codes and tokens for it in the same
  transaction, so restoring access never revives them. `clientAccess` in
  `listClients` lists managed clients only.
- Deleting a resource revokes every client's authorization for it, and creating one
  clears anything stored under its identifier, so recreating it revives nothing.
  API-key permissions are kept.
- `revokeClient` takes an optional `resource` to revoke one connection instead of
  all. `deleteClient` deletes any client; an automatic one can register again.
- `listClients` returns `connections`, what each client holds per resource: a consent,
  a live refresh token, or both. Each has its scopes (the consent's, else the newest
  token's), `approvedAt` (null without a consent, as for managed clients) and
  `refreshedAt`, when its newest live refresh token was issued. A managed client shows
  a connection only while it holds a refresh token.
- Dynamic registration ignores a `resources` list instead of refusing names outside
  the catalog.

## Administration

- `clankerauth:admin` is replaced by two scopes. `clankerauth:read` allows the listing
  tools, and `clankerauth:write` allows every tool. A changing tool called without
  `clankerauth:write` fails with `Forbidden`.
- Protected-resource metadata advertises `clankerauth:read`, `clankerauth:write` and
  `offline_access`, and the challenge requests both administration scopes. A token
  with neither gets `insufficient_scope` naming `clankerauth:read`.
- The built-in administration resource is fixed: every start restores its name and
  scopes, and `updateResource` and `deleteResource` refuse it with
  `The administration Resource is fixed`.

## Dashboard

- Each client card leads with its connections, with **Revoke** per connection and
  **Revoke all**. Only managed clients have an access form. Resource cards list
  their connected clients. Automatic clients can be deleted.
- The consent screen lets the owner untick requested scopes and grant only the rest;
  at least one must stay ticked when any were requested.
- The built-in administration resource has no edit form.

## Development package

- `CurrentOwner` carries `writable` instead of scopes; the disposable issuer's owner
  is writable. The embedded server behaves as above.
