# 0.13.0 — effect-actions 0.10.0, declared resources, flat issuer routes

Breaking for the SDK, the issuer and the development package: release and upgrade the three
together.

## Upgrade

Install `@gjermundgaraba/effect-actions` `0.10.0` if you use the `/session` or
`/effect-actions` entry points; the optional peer is `^0.10.0`. Upgrade the issuer, the SDK and
`@gjermundgaraba/clankerauth-dev` in one step: an SDK from before this release cannot read a
new issuer's key list, and a new SDK cannot read an old issuer's.

## Issuer routes

The issuer's API is one effect-actions binding with flat routes, `POST /api/<action>`.

| 0.12.0                              | 0.13.0                  |
| ----------------------------------- | ----------------------- |
| `POST /api/issuer/keyList`          | `POST /api/keyList`     |
| `POST /api/issuer/setupStatus`      | `POST /api/setupStatus` |
| `POST /api/issuer/setupOwner`       | `POST /api/setupOwner`  |
| `POST /api/administration/<action>` | `POST /api/<action>`    |

- The old paths answer 404. An SDK from 0.12.0 or earlier against a new issuer gets that 404
  for the key list. A resource that already holds a list keeps deciding keys from it until the
  list's 24-hour lifetime ends; past that, or before it has read any list, it refuses every API
  key as `ProviderUnavailable`. Access tokens still verify.
- The OpenAPI document is still `GET /openapi.json`, now of the one binding.

## SDK: a resource is declared, by its authentication descriptor

effect-actions 0.10.0 has contracts state who may call them, `caller: CurrentPrincipal`, and a
binding or MCP endpoint name how a caller proves it: a named authentication descriptor, whose
provider verifies every protected route and tool call. `Resource.make(options)`, the resource
value it returned, `Resource.middleware(resource)`, `resource.discovery` and
`resource.authorize` are gone. A resource is declared once at module level from the descriptor
its bindings name, its scopes and the one every credential carries, and what varies by
deployment comes where the application starts. The SDK no longer decides which scope an action
needs: the application does, with the check the resource offers.

Before, 0.12.0, on effect-actions 0.9.0:

```ts
// `Notes` is an `ActionGroup` whose actions declare `access: "read"` or `access: "write"`.
const Http = ActionHttp.make({ apiPath: "/api", errors: authenticationErrors }, Notes, Session);
const app = Notes.implement(handlers);

const routes = Layer.unwrap(
  Effect.gen(function* () {
    const notes = yield* Resource.make({
      issuer,
      publicUrl,
      scopes: { read: "notes:read", write: "notes:write" },
    });

    return Layer.mergeAll(
      notes.discovery.layer,
      Http.layer([app, notes.session], { before: notes.authorize }).pipe(
        Layer.provide(Resource.middleware(notes).layer),
      ),
      ActionMcp.layerHttp([app], {
        name,
        version,
        path: "/mcp",
        errors: authenticationErrors,
        before: notes.authorize,
      }).pipe(Layer.provide(Resource.middleware(notes).layer)),
    );
  }),
);
```

After, 0.13.0:

```ts
// contracts.ts, browser-safe: every protected contract states `caller: CurrentPrincipal`.
import { CurrentPrincipal, Whoami } from "@gjermundgaraba/clankerauth-sdk/session";

// The descriptor declares what its verifier fails with besides a refusal: the 503.
export const Login = Authentication.make("notes.Login", CurrentPrincipal, {
  error: ProviderUnavailable,
});

export const Http = ActionHttp.make([...actions, Whoami], { authentication: Login });

// server.ts
export const NotesResource = Resource.make(Login, {
  scopes: ["notes:read", "notes:write"], // every scope it has, published in discovery
  required: "notes:read", // every credential must carry it; every 401 names it
});

// The application's own rule: which actions need which scope.
const authorize = (action: Action.Any) =>
  action.readOnly ? Effect.void : NotesResource.requires("notes:write");

const app = Action.implement(actions, handlers, { authorize });

Layer.mergeAll(
  ActionHttp.layer(Http, [app, NotesResource.session]),
  ActionMcp.layerHttp(app, { name: "notes", version: "1.0.0", authentication: Login }),
).pipe(
  Layer.provide(NotesResource.provider),
  Layer.provide(NotesResource.layer({ issuer, publicUrl })),
);
```

- The descriptor declares `error: ProviderUnavailable`, and the binding declares nothing for
  it: every protected endpoint of a binding naming the descriptor declares it, so a typed
  client decodes the 503 as `ProviderUnavailable` on protected actions; a public one never
  answers it. `Resource.make` takes only a descriptor declaring it: one that does not is a
  type error there. `Resource.Login<Name>` and `Resource.Declared<Name>` take what the
  descriptor declares as an optional second parameter, `ProviderUnavailable` alone by
  default.
- A resource's scopes are typed: `make` infers them from `scopes`, and `Declared` and `Built`
  carry them as an optional last parameter. `requires(scope)`, `admitted(scope?)`,
  `admit(header, scope?)` and `watch(header, scope?)` take only a scope the resource declares,
  so `requires("notes:wirte")` is a type error. An annotation that leaves the parameter out
  accepts any scope string.
- `CurrentPrincipal` moves to the browser-safe `/session` entry, beside `Whoami`, which now
  states `caller: CurrentPrincipal`. `/effect-actions` no longer exports it: `/session` is its
  one path.
- `scopes` moves from the layer's options to `make`: they are the same in every deployment. Its
  `{ read, write }` shape is gone. `scopes` lists every scope the resource has, published in
  discovery, and `required` names the one every credential must carry, as `read` did: the
  verifier requires it and every 401 names it. `required` is one of `scopes`, as the types
  check. `{ read: "notes:read" }` becomes `{ scopes: ["notes:read"], required: "notes:read" }`.
- The SDK has no scope policy of its own: `authorize`, the rule mapping an action's access to
  `write`, is gone. The application writes its rule as its implementation's authorizer, with
  `requires(scope)`, an `Effect<void, Action.Forbidden, CurrentPrincipal>`: a caller without
  the scope is refused with a `Forbidden` naming it, on which an OAuth client steps up; an
  API key's names none. 0.12.0's rule, a write needing the write scope, is
  `(action) => action.readOnly ? Effect.void : NotesResource.requires("notes:write")`. It reads
  only the caller, so implementations are module-level values and need no built resource. A
  single-scope resource has nothing more to require: `{ authorize: Action.allowAll }`.
- `admit(header, scope?)` and `watch(header, scope?)` take an optional scope instead of an
  access level, effect-actions' `Action.Access`, which 0.10.0 removes: `admit(header, "read")`
  becomes `admit(header)`, any verified caller, and `admit(header, "write")` names the scope,
  `admit(header, "notes:write")`. They share `requires`' check.
- `Resource.Scopes`, the `{ read, write }` shape, is gone, and so is `Resource.CurrentPrincipal`:
  import `CurrentPrincipal` from `/session`.
- `Resource.Resource` was the built resource, and is now its service identity,
  `Resource.Resource<Name>`. The built value is `Resource.Built`: an annotation
  `notes: Resource.Resource` becomes `notes: Resource.Built`.
- An authorizer is the application's own
  `(action: Action.Any) => Effect<void, Action.Forbidden, CurrentPrincipal>`; what `admitted`
  returns is effect-actions' `Authentication.Protection<CurrentPrincipal, Name>`.
- `watch` fails with the refusal `admit` would then answer, `Action.Refusal` or
  `ProviderUnavailable`, in place of the verifier's `Unauthorized` and `InsufficientScope`: an
  expired token ends it as `Unauthenticated`, a key losing the scope as `Forbidden`.
- `provider` is the descriptor's provider, effect-actions' `Authentication.layer`: provide it
  to every layer serving the resource's protected actions. It publishes RFC 9728 discovery
  itself. `discovery: false` publishes none, for a surface whose callers only hold API keys.
  It is a layer, not router middleware: middleware of your own is router middleware provided
  after it, or an HTTP layer's `middleware`, never combined with it.
- `layer(options)` builds the resource alone, and needs no router: `admit` and `watch`, for a
  caller outside the router, read only it.
- `admitted(scope?)` admits a route of the application's own, such as a page frame, a file or
  an OpenAPI document, as the actions are: effect-actions' `Authentication.protect` with the
  resource's descriptor, and `scope`, if given, checked inside it with `requires`. It is an
  `Authentication.Protection<CurrentPrincipal, Name>`. It provides the route its
  `CurrentPrincipal` and answers it as an action route: the same refusals, 503 included,
  `Cache-Control: no-store` unless the route states its own caching, and a refusal or 401 of
  the route's own challenged. Its layer requires `provider`; `combine` puts middleware of your
  own reading the caller inside it.
- `local(subject)` is the process's principal on a trusted local surface, stdio MCP or a local
  command: `actor: { kind: "local" }`, every declared scope, no expiry.
  `Effect.provideService(CurrentPrincipal, NotesResource.local("owner"))`, around the same
  implementation, whose authorizer admits it, as it holds every scope.
- `CurrentPrincipal` carries a `Caller`, exported by `/session`: a
  verifier's principal or the process, whose `actor` adds the `"local"` kind, so a `switch` over
  `CurrentPrincipal`'s actor handles one more case. `Verifier.Principal`, what `verifyToken` and
  `admit` give, stays a client or a key, and is a `Caller`. Code typed `Verifier.Principal` that
  takes `CurrentPrincipal` takes `Caller` instead.
- `session` answers `Whoami`, which is one action, bound beside your own: `POST <prefix>/whoami`,
  called as `api.whoami()`. Serve it over HTTP only.
- `yield* NotesResource.service` gives the built resource: `admit` and `watch` for a caller
  outside the router, `verifier`, `issuer`, `resource`.
- Two resources in one process, such as two listeners with different scopes, are two
  descriptors, each named by its own binding, and two resources: each guards its own surface
  in any layer graph.
- `Resource.authenticate(verifier, token)` takes the token the descriptor's scheme decodes,
  for a provider of your own around a verifier of your own. It fails with a refusal or
  `ProviderUnavailable`, which that provider's descriptor declares too.
- A scope that is no OAuth scope token, such as `"notes write"`, is refused by effect-actions
  when the provider builds the discovery it publishes: the SDK checks no scope syntax of its
  own. With `discovery: false`, nothing checks it.

Before, a route of the host's own and a local surface, 0.12.0 patterns:

```ts
// A route of the host's own, admitted by hand.
HttpRouter.add(
  "GET",
  "/frame",
  Effect.gen(function* () {
    const { headers } = yield* HttpServerRequest.HttpServerRequest;
    const admission = yield* notes.admit(headers.authorization, "read");

    if (!admission.ok)
      return HttpServerResponse.fromWeb(new Response(admission.refusal.body, admission.refusal));

    return yield* frame(admission.principal);
  }),
);

// A local surface: no `before`, and an invented OAuth client for handlers reading the caller.
const processPrincipal = {
  subject,
  scopes: [READ, WRITE],
  actor: { kind: "client", clientId: "stdio" },
  expiresAt: undefined,
};
ActionMcp.layerStdio([Notes.implement(handlers)], options).pipe(
  Layer.provide(Layer.succeed(CurrentPrincipal, processPrincipal)),
);
```

After, 0.13.0:

```ts
// The route reads its caller from `CurrentPrincipal`.
HttpRouter.add("GET", "/frame", frame).pipe(Layer.provide(NotesResource.admitted().layer));

// The same implementation as every remote surface, its authorizer included.
ActionMcp.runStdio(app, options).pipe(
  Effect.provideService(CurrentPrincipal, NotesResource.local(subject)),
);
```

## SDK: verification takes a token

`verifier.verify(authorization)` is removed; `verifier.verifyToken(token)` remains. A route's
token is what effect-actions' native bearer scheme decodes, and `admit` and `watch` read a
header with its `Authentication.bearerTokenOf`, so a route and a socket accept the same
headers. Leading spaces and tabs are ignored, `Bearer` is matched case-insensitively, as
before, and is followed by one or more spaces; the rest of the header, without trailing spaces
or tabs, is the token, whatever it holds. 0.12.0 took exactly one space and a token without
whitespace or commas. A caller of the root entry extracts the token itself.

## Refusals on the wire

Refusals are effect-actions' built-in errors, on HTTP, MCP and from `admit`.

| Case                        | 0.12.0                                       | 0.13.0                                                                                                                     |
| --------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| No credential               | 401 `{"_tag":"Unauthorized","message":…}`    | 401 `{"_tag":"Unauthenticated","message":"A bearer token is required."}`, refused before verification                      |
| Bad credential              | 401 `{"_tag":"Unauthorized","message":…}`    | 401 `{"_tag":"Unauthenticated","message":…}`                                                                               |
| Missing scope, access token | 403 `{"_tag":"InsufficientScope","scope":…}` | 403 `{"_tag":"Forbidden","message":"Requires <scope>.","scopes":[…]}` with an `insufficient_scope` challenge, over MCP too |
| Missing scope, API key      | 403 `{"_tag":"InsufficientScope","scope":…}` | 403 `{"_tag":"Forbidden","message":"Requires <scope>."}`, no challenge; a tool error over MCP                              |
| Issuer unreachable          | 503 `ProviderUnavailable`                    | unchanged                                                                                                                  |

- `Unauthorized` and `InsufficientScope` remain the `Verifier`'s failure types, as plain tagged
  errors; they are no longer schemas. `authenticationErrors` is removed: the descriptor
  declares `error: ProviderUnavailable`. `InsufficientScope` also carries the credential's
  `actor`, which decides whether its `Forbidden` names the scope to step up to: only an OAuth
  client's does. `Unauthorized`'s `message` is optional, `Authentication required` by
  default, which an expired token watched by `watch` ends with too.
- The 403's `insufficient_scope` challenge carries the refusal's message as its
  `error_description`, when RFC 6750 allows its characters.
- On the issuer's own routes, a provider 401 or 403 is answered as
  `{"_tag":"Forbidden","message":…}`; its other errors keep `error`.
- The issuer's actions no longer declare an `Unauthorized` of their own: a request the issuer
  cannot authenticate answers the built-in `Unauthenticated` (401), which every protected
  endpoint and tool declares, where 0.12.0 answered `{"_tag":"Unauthorized","error":…}` (see
  the owner session below and the administration MCP endpoint).
- Input an issuer action cannot decode, and input it decodes but its own checks refuse, such
  as a grant on an unknown resource or scope, an expiry in the past, a resource identifier
  that is not canonical or has a fragment, the reserved scope `offline_access` among a
  resource's scopes, the administration resource named to update or delete, or a client's
  access to an unknown resource, answers the built-in
  400 `{"_tag":"InvalidInput","message":…,"issues":[{"path":[…],"message":…}]}`, naming the
  field, where 0.12.0 answered `{"_tag":"BadRequest","error":…}`. `BadRequest`, with an
  `error` message and no field, remains for input the provider rejects, such as a short
  password, an invalid email, a duplicate resource identifier or a redirect URI the client's
  type does not allow; for a request body the issuer cannot read; and for a request the issuer
  refuses for its state, such as setting the access of an automatic client. A client handles
  both.
- The input rules that read no stored state are in the issuer's input schemas, so the OpenAPI
  document and the MCP tools' input schemas state them: an API key's name has 1–100
  characters and is not blank; a key's grants name at least one resource, each with at
  least one scope, named once; a resource's name is not blank and each of its scopes is an
  OAuth scope token; a client's resources are named once each. Their `issues` keep their
  sentences, and a malformed scope is named by its index, `["scopes", 1]`. A typed client,
  the dashboard's included, refuses such input before sending it, with the same
  `InvalidInput`.
- The issuer's administration actions are owner-protected contracts: the dashboard's session
  cookie is one descriptor on the HTTP binding, which the server builds where it starts with
  `ownerSession(<the deployment's cookie name>)` (`OwnerSession` is the browser's), and the MCP
  endpoint's access token another, `OwnerToken`. A dashboard call without a session answers 401
  `{"_tag":"Unauthenticated",…}`, where 0.12.0 answered `{"_tag":"Unauthorized","error":…}`.
  Both descriptors declare the issuer's own errors, which every administration action
  declares, so a failure while authenticating the owner, such as the issuer's data being
  unreachable, answers as an action's does, `ServiceUnavailable` with 503 included.

## Issuer: the administration MCP endpoint

`/mcp` refuses as effect-actions' bearer surfaces do, with HTTP statuses and challenges rather
than tool results.

| Case                                  | 0.12.0                                                                | 0.13.0                                                                                                                                             |
| ------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| A changing tool, read-only token      | tool result with `isError: true` and `{"_tag":"Forbidden","error":…}` | HTTP 403 with an `insufficient_scope` challenge naming `clankerauth:write`, body `{"_tag":"Forbidden","message":…,"scopes":["clankerauth:write"]}` |
| No or a rejected token, unknown owner | 401 `{"_tag":"Unauthorized","error":…}`                               | 401 `{"_tag":"Unauthenticated","message":…}`, with its challenge                                                                                   |

- An OAuth client steps up on the 403, as it does on any resource's: a client that treated
  the tool error as final now sees an HTTP error and can ask for the write scope.

## Issuer: the owner session cookie

The dashboard's owner session is the provider's session cookie, named as in 0.12.0:
`better-auth.session_token` over HTTP and `__Secure-better-auth.session_token` over HTTPS.
`OwnerSession` names it as an `apiKey` in a cookie, and a descriptor names one cookie, so the
issuer builds its descriptor, and the binding naming it, where it starts, from the name its
sessions use; its `/openapi.json` names that cookie. A browser needs no name: it sends its
cookies itself.

- Owners stay signed in across the upgrade: the cookie is the one they already hold.
- The `__Secure-` prefix stays over HTTPS, so browsers let only an HTTPS response set or
  overwrite the session cookie.
