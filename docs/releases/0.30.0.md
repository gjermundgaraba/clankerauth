# 0.30.0 — Breaking: effect-actions 0.21.0 peers, branded contract errors, finite secret expiry, and no secret fields for public clients

Breaking for applications on effect-actions 0.20, for TypeScript code that builds or assigns the administration contract's or the SDK's error classes structurally, and for clients that read `client_secret: null` from `createClient`. The database, the configuration and the SDK's verification are as in 0.29.1, so an application on SDK 0.29.1 verifies against a 0.30.0 issuer and the reverse. Every package and the server go to 0.30.0 to keep one version across the release.

## Upgrading

1. **effect-actions 0.21.0.** The SDK's optional and the administration contract's `@gjermundgaraba/effect-actions` peer is `^0.21.0`, formerly `^0.20.0`; the two ranges do not overlap, so an application on 0.20 moves to 0.21 with them. effect-actions 0.21.0 requires Effect `~4.0.5`, so the administration contract's `effect` peer is `~4.0.5`, formerly `~4.0.4`; the SDK's stays `~4.0.4` for an application that verifies without effect-actions. Of its breaking changes, the one most likely to reach application code is that its own tagged errors (`Action.InvalidInput`, `Action.Unauthenticated`, `Action.Forbidden` and others) are branded as this release's are: make each with its class. Its changelog lists the rest.
2. **Branded error classes.** The administration contract's errors (`InternalServerError`, `ServiceUnavailable`, `ClientNotFound`, `ResourceNotFound`, `ApiKeyNotFound`, `ClientIsAutomatic`, `OwnerExists`, `ProviderRefused`, `UnreadableRequest`) and the SDK's `ProviderUnavailable` and `ConfigurationError` carry a brand, so TypeScript checks them nominally. An object literal or another class with the same fields no longer type-checks as one of them; construct the class (`new ClientNotFound({ … })`, or its `of`) instead. Their `_tag`s, fields, constructors, status codes and wire form are unchanged.
3. **Public clients' credentials.** For a client created with `token_endpoint_auth_method: "none"`, `createClient` leaves `client_secret` and `client_secret_expires_at` out, as RFC 7591 does for a client without a secret, where 0.29.1 sent both as `null`. The administration contract's client already read both as absent. Code that reads the HTTP or MCP response directly and tests for `null` should test for a missing field instead.

## Administration contract

- The `@gjermundgaraba/effect-actions` peer is `^0.21.0` and the `effect` peer `~4.0.5`.
- `ClientCredentials.client_secret_expires_at` is a finite number (`Schema.Finite`). Its JSON Schema, in the OpenAPI document and the MCP tool schemas, no longer admits `"NaN"`, `"Infinity"` or `"-Infinity"`, and the contract's client refuses them. The issuer never sent them.
- The error classes listed above are branded.

## SDK

- The optional `@gjermundgaraba/effect-actions` peer is `^0.21.0`.
- `ProviderUnavailable` and `ConfigurationError` are branded. `ProviderUnavailable` keeps its constructor, `new ProviderUnavailable({ operation, cause })`.

## Issuer

- Built on effect-actions 0.21.0.
- `createClient` and `rotateClientSecret` leave out any secret field the client does not have, instead of sending it as `null`.

## CLI and development package

- Built on effect-actions 0.21.0. Each carries its own copy, so installing it needs nothing new.
- `DevServerLike`, the server type the `/edge` entry's helpers take, declares `use` and `on` as properties rather than methods. Vite's dev server still fits. A hand-written stand-in whose handler parameters are narrower than Connect's or Node's no longer type-checks.
