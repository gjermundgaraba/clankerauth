# 0.3.0 — action API (unreleased)

This is a breaking issuer and SDK release. Both
`@gjermundgaraba/clankerauth-node` and `@gjermundgaraba/clankerauth-dev`
are prepared at 0.3.0.

## API changes

- Custom operations use `POST /api/<groupName>/<actionName>`; no-input calls
  send `{}`. Issuer actions live under `issuer`; owner operations under
  `administration`. The old `/admin/*`, `/api/setup`, `/api/api-keys/verify`,
  and ungrouped `/api/<actionName>` routes are removed, without aliases or
  retry fallbacks.
- API-key verification moves to `POST /api/issuer/verifyApiKey`, with the same
  bearer credential and resource payload. The Node SDK uses this path.
- Malformed HTTP input returns sanitized tagged `BadRequest` JSON (400);
  invalid output returns `InternalServerError` JSON (500). MCP uses native tool
  errors: declared domain failures are JSON text with `isError: true`; schema
  failures use native validation/internal-error messages. Successful tool
  results use `structuredContent.value`.
- Owner administration is also available through MCP. Setup and key verification
  remain HTTP-only actions. OAuth protocol endpoints and `/healthz` are unchanged.
- Authenticated `GET /openapi.json` no longer requires Origin. Administration and
  HTTP POSTs retain the configured-Origin check and owner-session authentication.
- MCP uses OAuth bearer authentication for the built-in `<AUTH_BASE_URL>/mcp`
  resource and `admin` scope. Cookie-authenticated MCP requests are removed.
  Public protected-resource metadata enables automatic onboarding and owner consent;
  `offline_access` enables refresh and is advertised as an optional capability;
  authentication challenges request `admin` alone.
- Administration API-key grants are rejected: administration requires OAuth.
  Dashboard key renaming does not replace permissions; grant editing is explicit.
- Browser-session expiry and dashboard sign-out do not revoke MCP access.
  Offline refresh grants survive dashboard sign-out; explicit client revocation
  or blocking ends delegated access.
- Resource listings expose `builtIn`. The administration resource can be renamed,
  but its scopes and identifier remain fixed and deletion is prohibited.
- `MCP_ALLOWED_ORIGINS` enables exact additional browser origins for MCP, with
  preflight and exposed challenge/session headers. Dashboard CSRF policy is separate.
- Provider sessions are acquired only for operations requiring provider session
  credentials. Protocol discovery and identity-only actions do not create sessions.
- Revoking or blocking a client invalidates its administration MCP access tokens
  immediately. Random live-client grant generations prevent old tokens from becoming valid after re-consent or client recreation.
- Generation checks also fence token issuance against concurrent revocation and
  metadata reconciliation. Refresh CAS and replacement insertion commit together;
  unrelated clients' metadata changes no longer reject exchanges.
- Token generation uses provider-resolved identity, including assertion-only
  `private_key_jwt` and case-insensitive Basic authentication.
- MCP enables the 2026-07-28 and 2025-11-25 / 06-18 / 03-26 revisions over
  Effect's native Streamable HTTP transport, which streams responses. Historical
  two-endpoint SSE remains unsupported.

## Development database reset

This pre-release requires a fresh database. Recreate development databases from
before this change; their trigger definitions and automatic-client resource links
are not upgraded. There are no existing live installations to migrate.

The server creates its administration resource at startup and stores a random grant
generation on each live client for MCP revocation. Managed-client consent policy is set at creation.

Deleting an ordinary resource retains stored authorization grants and API-key
permissions; recreating its identifier can restore access.

The effect-actions dependency is the published `0.1.0-rc.2` release; the
previous checked-in local snapshot has been removed.
