# 0.9.0 — clankerauth by its full name

Breaking for both packages and the server. Both `@gjermundgaraba/clankerauth-sdk`
and `@gjermundgaraba/clankerauth-dev` are prepared at 0.9.0. Every name the
server, the packages and the documentation used for this product is now
`clankerauth`, in lowercase. Nothing reads the old names: start the issuer on a
fresh database and upgrade the server, the SDK and the development package
together.

## Server configuration

Every variable the server reads is prefixed with `CLANKERAUTH_`, including the
secret, the bind address, the port and the proxy flag. The secret is read from
`CLANKERAUTH_BETTER_AUTH_SECRET` and passed to Better Auth as its secret. The old names
are ignored, so a server started with them falls back to the defaults or refuses
to start without `CLANKERAUTH_BASE_URL` and `CLANKERAUTH_BETTER_AUTH_SECRET`.

| 0.8.0                 | 0.9.0                             |
| --------------------- | --------------------------------- |
| `AUTH_BASE_URL`       | `CLANKERAUTH_BASE_URL`            |
| `AUTH_DATABASE`       | `CLANKERAUTH_DATABASE`            |
| `AUTH_COOKIE_DOMAIN`  | `CLANKERAUTH_COOKIE_DOMAIN`       |
| `HOST`                | `CLANKERAUTH_HOST`                |
| `PORT`                | `CLANKERAUTH_PORT`                |
| `TRUST_PROXY`         | `CLANKERAUTH_TRUST_PROXY`         |
| `MCP_ALLOWED_ORIGINS` | `CLANKERAUTH_MCP_ALLOWED_ORIGINS` |
| `ALLOW_INSECURE_HTTP` | `CLANKERAUTH_ALLOW_INSECURE_HTTP` |
| `BETTER_AUTH_SECRET`  | `CLANKERAUTH_BETTER_AUTH_SECRET`  |

- The default database file is `data/clankerauth.sqlite`, and the container's is
  `/data/clankerauth.sqlite`. A deployment that relied on the default
  `auth.sqlite` starts on an empty database unless it sets
  `CLANKERAUTH_DATABASE` or renames the file (with its `-wal` and `-shm`).
- The container sets `CLANKERAUTH_HOST`, `CLANKERAUTH_PORT` and
  `CLANKERAUTH_DATABASE`, and its health check reads `CLANKERAUTH_PORT`.
- Configuration errors name the new variables.

## API keys

- New keys start with `clankerauth_` instead of `ca_`.
- The issuer verifies only `clankerauth_` keys: a `ca_` key is `401` at
  `verifyApiKey` and is not recognised as a key by the SDK. Mint new keys.

## Administration

- The built-in administration resource's scope is `clankerauth:admin`, not
  `admin`: its protected-resource metadata advertises
  `["clankerauth:admin", "offline_access"]` and its challenge requests
  `scope="clankerauth:admin"`. MCP clients consent again for the new scope.
- The built-in resource is seeded as **clankerauth administration**. The
  provider seeds it once, so a database created by an earlier version keeps the
  `admin` scope, which no longer authorizes MCP. Start on a fresh database.
- The Better Auth application name, the dashboard title and the start-up log
  line (`clankerauth ready`) say `clankerauth`.

## SDK

- `Verifier` and `Resource` treat a bearer that starts with `clankerauth_` as an
  API key and verify it online; anything else is a JWT. SDK 0.8.0 would treat a
  0.9.0 key as a JWT and refuse it, and SDK 0.9.0 refuses a 0.8.0 key the same
  way, so an application upgrades the SDK together with the issuer. No export
  changes shape.

## Development package

- With a `cookieDomain`, the disposable issuer is
  `http://clankerauth.<cookieDomain>:<port>`, not `http://auth.<cookieDomain>:<port>`.
  An application that reads `issuer.url` and `issuer.issuer` is unaffected; one
  that hard-codes the host, for example in a Vite `forwardAuth({ issuer })` or a
  proxy config, changes it.
- `issuer.apiKey(...)` and the fake issuer's `apiKey(...)` return
  `clankerauth_` keys, so a test that uses them needs SDK 0.9.0, and a test
  that asserts the `ca_` prefix changes it.
- An invalid `cookieDomain` is refused with a message naming
  `CLANKERAUTH_COOKIE_DOMAIN`.
- The package's description and README say clankerauth; its README's workspace
  example keeps its state in `.dev/clankerauth`.

## Internal

- The Effect service keys are `clankerauth/Auth`, `clankerauth/CurrentOwner`
  and `clankerauth/ResponseCookies`.
- `pnpm dev` keeps its database at `.dev/clankerauth.sqlite`, so a local
  development issuer starts fresh once.
