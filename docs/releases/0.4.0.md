# 0.4.0 — unpatched provider

This is a breaking issuer and SDK release. Both
`@gjermundgaraba/clankerauth-sdk` and `@gjermundgaraba/clankerauth-dev`
are prepared at 0.4.0. It requires a fresh database; there are no live
installations to migrate.

## Packages

- The SDK is `@gjermundgaraba/clankerauth-sdk`, replacing
  `@gjermundgaraba/clankerauth-node`. Same exports and subpaths; only the
  package name changes.
- Both packages are published to npm instead of GitHub Packages, so installing
  them needs no registry configuration or token. Earlier versions stay on
  GitHub Packages and are not updated.
- The optional `@gjermundgaraba/effect-actions` peer is the 0.1.0 release.

## Provider

- The pnpm patches to `@better-auth/oauth-provider` and `@better-auth/api-key`
  are removed. The provider runs as published.
- Access tokens no longer carry a `grant_generation` claim, and the SDK no
  longer requires one. A client principal is `{ kind: "client", clientId }`.
- Revoking or blocking a client, or deleting it, ends refresh immediately but
  cannot recall an already-issued access token; it expires within fifteen
  minutes. Administration MCP rejects tokens whose client is blocked or gone.
- Blocking uses the provider's `disabled` flag. The `clientOnboarding` table,
  its triggers, the 1,000-client capacity cap and the seven-day cleanup of
  abandoned registrations are removed.
- CIMD metadata changes no longer revoke grants.
- API-key listing shows at most the first 100 keys, and the per-key rate limit
  uses the plugin's inactivity-based window.
- Owner setup goes through the provider's email sign-up and signs the owner in:
  `setupOwner` returns the session cookie, and the dashboard opens directly
  after setup. The `serviceOwner` table is removed: the owner is the only user,
  a user-creation hook rejects a second account, and concurrent setup requests
  are serialized so the loser gets a conflict. Email validation is the
  provider's; the extra 254-character limit is gone.
- The built-in administration resource is seeded through the provider's
  `resources` option instead of a direct row insert.
- Dynamic registration stays limited to ten per peer per minute, now configured
  on the provider plugin rather than as a core custom rule.
- Provider 422 responses surface as `BadRequest` instead of a generic server
  error.

## Token policy

- Access tokens last fifteen minutes.
- Refresh tokens keep a thirty-second reuse window: a retried refresh returns
  the same replacement instead of revoking the family.
- Token requests may omit `resource`; authorization requests still name exactly
  one.

## Administration

- `createClient` uses provider vocabulary: `client_name`, `redirect_uris` (one
  or more), `token_endpoint_auth_method` (`none`, `client_secret_basic` or
  `client_secret_post`) and `application_type` (`web` or `native`) replace
  `name`, `redirect`, `confidential` and `native`.
- New `updateClient` action renames a managed client or changes its redirect
  URIs and application type. The provider cannot change the authentication
  method after registration.
- Provider errors surface their own descriptions, and a provider refusal on an
  owner-authenticated action is reported as `Forbidden`. Creating a resource
  with an existing identifier is a `BadRequest` from the provider.
- `setClientAccess` also applies to automatically registered clients.
- Resources accept any absolute URI without a fragment and may define no custom
  scopes.
- API-key expiry is no longer capped at one year.
- Owner actions and `setupOwner` no longer require an `Origin` header; the
  SameSite session cookie is the CSRF boundary. MCP still validates Origin.

## Deployment

- `TRUST_PROXY=true` attributes requests to the last `X-Forwarded-For` hop.
- `ALLOW_INSECURE_HTTP=true` permits a plain-HTTP issuer and MCP origins beyond
  loopback.
- Hashed dashboard assets are served immutable, and JWKS and discovery
  documents are cacheable for five minutes. Everything else stays `no-store`.
- Request bodies are limited through Effect's `MaxBodySize` reference instead
  of application buffering; an oversized upload is disconnected rather than
  answered with 413.
- Password changes require a fresh session again (provider default).
