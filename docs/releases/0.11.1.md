# 0.11.1 — new API keys work within seconds

Not breaking. The issuer's endpoints and the key list format are unchanged, so an
application on SDK 0.11.1 verifies against a 0.11.0 issuer and the reverse. Both
packages and the server go to 0.11.1 to keep one version across the release.

## SDK

- A key the held list does not name has the list read again before it is refused, unless
  the list was read within the last five seconds. A key created, enabled or granted on
  the resource therefore works within seconds; in 0.11.0 it was refused until the next
  minute's read.
- A key the list names is still decided without issuer traffic, for a minute per read,
  so a key disabled, deleted or re-scoped keeps the access it had for up to a minute. A
  key's expiry still applies at once.
- A held list past its 24-hour window is read again after five seconds, where 0.11.0
  waited out the rest of the minute. Only a list that arrived close to its expiry,
  delayed or replayed, reaches that point inside the minute, since the issuer signs a
  fresh one on every read. Until a read succeeds, a key is still `ProviderUnavailable`.
- Unknown keys can now reach the issuer, at most once every five seconds per resource
  server, where 0.11.0 refused them from the held list alone. A read that fails holds
  off the next one for the same five seconds, and the held list decides meanwhile.

## Issuer

- The dashboard's API-key help says that a new key works within seconds.

## Development package

- It embeds the 0.11.1 server.
