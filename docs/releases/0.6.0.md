# 0.6.0 — one resource per app, one authorization rule

Breaking for both packages and the server. Both `@gjermundgaraba/clankerauth-sdk`
and `@gjermundgaraba/clankerauth-dev` are prepared at 0.6.0. There are no live
installations to migrate.

The five applications behind this issuer each hand-rolled the same four things:
a write-scope policy derived from an MCP display hint, an `InsufficientScope`
error, a host/origin request policy, and a development forward-auth edge. All
four now live here, tested once.

## Resource identity

- A resource identifier is **one per app, at the public origin root**, written
  with its trailing slash: `https://notes.example/`. One resource then covers
  `/api`, `/mcp` and any socket, with one RFC 9728 document at
  `/.well-known/oauth-protected-resource` and one `forward_auth` block.
- `Resource.make` refuses an identifier that is not already canonical
  (`new URL(id).href === id`), with `ConfigurationError`. An MCP client sends
  `new URL(metadata.resource).href` and the token audience is that string, so an
  identifier the client would rewrite silently fails to match the issuer's
  registered resource. `https://notes.example` is refused; the message names the
  form to use.
- The official MCP client accepts an origin-root resource for an endpoint under
  it: `checkResourceAllowed` compares origins and treats the configured path as a
  prefix. A test in `packages/sdk/tests/authorization.test.ts` pins this against
  the published client.

## SDK

- New `InsufficientScope` (403). It names **only** the missing scope, so a
  refusal never enumerates a resource's permissions. Exported from both the root
  and `/effect-actions`; declare it in the group's `errors`.
- `Resource.make` takes an optional `writeScope`. `resource.authorize` is then a
  ready effect-actions `before` hook: a read passes, a write needs that scope.
  Without `writeScope` it passes everything, so a single-scope resource has no
  authorization code at all. An application names two scopes and writes none.
- New `resource.admit(authorization, access?)`, for callers outside an Effect
  router: a Node `upgrade` handler, a socket, a per-request endpoint. It returns
  either the principal or a ready-to-send refusal — status, headers and JSON body
  — using each error's own status (401/403/429/503), the RFC 6750 challenge
  including the no-credential case, and `Cache-Control: no-store`. `access:
"write"` also demands the write scope, so a socket can require it before it is
  established. `Resource.middleware` is built on the same function, so a router
  and a socket cannot answer differently.
- `Principal` gains `expiresAt`: an access token's verified `exp` in epoch
  milliseconds, so a host bounding a connection never decodes the token again. It
  is `undefined` for an API key, which carries no token lifetime and is
  re-verified against the issuer on every request; a host caching a key decision
  must choose its own bound.
- New `RequestPolicy` (root export). Forward auth makes a browser's credential
  ambient, so the app checks where a request came from before anything reads it:
  the `Host` header must equal the configured public host **as sent**, including
  its port, by string comparison with no URL parsing that can throw; a supplied
  `Origin` must be the public origin or in an explicit allow-list (a desktop
  shell's `wtf://app`); exempt paths answer without either check, for container
  probes. `policy.allows({ target, host, origin })` is the whole decision and
  takes no services, so a Node `upgrade` handler applies the same rule as
  `policy.middleware`.
- The optional `@gjermundgaraba/effect-actions` peer is 0.3.0. Actions now
  declare `access: "read" | "write"` (default `"write"`), which is what
  `authorize` reads; `mcp.readOnly` defaults from it. Derive authorization from
  `access`, never from a tool hint.

## Dev

- New `@gjermundgaraba/clankerauth-dev/edge`: the development forward-auth edge,
  written once. `check` asks the issuer over `node:http` — never `fetch`, which
  overwrites `Sec-Fetch-Mode` — relaying cookie and that header, setting
  `x-forwarded-proto/host/uri`, with a timeout, and rejecting a `204` that
  carries no `Authorization` rather than forwarding an empty one. `middleware`
  applies it to HTTP with configurable public paths and an
  already-has-a-credential bypass; `upgrade` checks and then proxies a socket to
  a backend, ending it on a normal close and destroying it only on error, and
  returns `false` for paths it does not own so a hot-reload socket is untouched;
  `attach` installs both on a plain Node server, and `forwardAuth` is the same as
  a Vite plugin. Nothing in the package imports Vite, at run time or in its types.
  `reserveLoopbackPort` claims a port before anything that must know its origin.
- `startDisposableIssuer` takes `dataDir` and `port`. With them the owner
  account, its password, the signing secret, the registered client and the
  database survive a restart; provisioning is idempotent, and the directory is
  never deleted. Without them nothing changes: a temporary directory, a random
  port, and everything removed by `close()`.
- The issuer now provisions what every application was scripting by hand:
  `apiKey({ permissions })` mints a scoped key, `ownerSession(appOrigin)` signs
  the owner in and seals the forward cookie the way a browser does (returning it
  both as a header and as name/value pairs for a browser harness), and
  `ownerToken({ resource, appOrigin })` returns an access token through the same
  forward-auth check. `port` is returned alongside `url`.

## Verified, not changed

`GET /forward-auth/logout?rd=<foreign origin>` answers **302 to `/login`**, not 400. Only `/forward-auth/continue` refuses an unusable `rd` with 400, because it
has nowhere to send the browser after sign-in; logout always ends the session
first and then falls back to the login page. `apps/server/tests/forward-auth.test.ts`
pins both.

## Migration

- Resource identifiers: replace `${publicUrl}/api` and `${publicUrl}/mcp` with
  one `new URL("/", publicUrl).href`, and register that one resource.
- Delete each application's `InsufficientScope`, `accessOf`/`isMutation`/
  `requiresWrite`/`isRead` and `authorize`. Declare `access` on the actions,
  import `InsufficientScope` from the SDK, pass `writeScope` to `Resource.make`
  and bind `{ before: resource.authorize }` on `implement`.
- Replace hand-written `admit`/`eventlogMiddleware` helpers with
  `resource.admit`, and hand-written host/origin middleware with
  `RequestPolicy.make(...).middleware`.
- Replace development forward-auth plugins and edges with
  `@gjermundgaraba/clankerauth-dev/edge`.
