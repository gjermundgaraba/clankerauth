# 0.28.1 — Administration keys, checked where keys live

Nothing to upgrade. The database, the configuration, the administration contract and the SDK's
API are as in 0.28.0. Every package and the server go to 0.28.1 to keep one version across the
release.

## Issuer

- An administration key whose stored permissions no longer decode is refused with
  `Unauthenticated` (401) and logged, as key lists leave such a key out; 0.28.0 answered every
  request with it `InternalServerError` (500).
- The lookup moves into the API-key service, beside the key lists, as `ApiKeys.holder`, so how a
  key is stored is known in one place. It is traced as `ApiKeys.holder`.

## Dashboard

- The API-key page says what a change to an administration key applies to at once: its
  administration access. A grant the same key holds on another resource still takes effect
  within about a minute, as any key's does.

## CLI

- A `CLANKERAUTH_URL` that names no origin, such as a `mailto:` URL, is refused with a message.
  With `CLANKERAUTH_TOKEN` set, 0.28.0 crashed with a stack trace on it.

## Documentation

- The issuer's README, the provider-integration notes, the domain language and the 0.28.0 notes
  say that only a key's administration grant is read on every request, not the whole key. The
  provider-integration notes no longer claim an administration request writes nothing: actions
  that call the provider open a temporary session, whatever the bearer.
- The CLI and administration-contract READMEs link to the issuer's README for what an
  administration key may do instead of restating it.
