# 0.16.0 — Administration at the origin root, over HTTP to tokens, and a CLI

Breaking for every client of administration: each authorizes again after the upgrade.
Applications are not affected. Their resources, access tokens, API keys and key lists are
unchanged, so an SDK at 0.15.0 verifies against a 0.16.0 issuer and the reverse. The SDK, the
development package, the server and the new CLI go to 0.16.0 to keep one version across the
release.

## Upgrade

Upgrade the issuer, then sign every administration client in again: each MCP client connected
to `/mcp`, and anything else holding an administration token. The upgrade clears the
authorization they held, so a refresh is refused and the client starts a new authorization,
with consent for an automatic one. A managed client keeps its access to administration, under
the new name.

A database that holds a resource of your own at the issuer's origin root, besides
administration, refuses to start and names it: delete that resource with 0.15.0 first.

## Administration is the issuer's origin root

The built-in administration resource was `<CLANKERAUTH_BASE_URL>/mcp`, after the first
endpoint that took its tokens. Every application's resource is its origin root, and so now is
the issuer's: `<CLANKERAUTH_BASE_URL>/`.

| 0.15.0                                          | 0.16.0                                      |
| ----------------------------------------------- | ------------------------------------------- |
| Resource `<CLANKERAUTH_BASE_URL>/mcp`           | Resource `<CLANKERAUTH_BASE_URL>/`          |
| `GET /.well-known/oauth-protected-resource/mcp` | `GET /.well-known/oauth-protected-resource` |

- The identifier names a token audience, not the routes that take one: the dashboard at `/`
  still takes the owner's session cookie alone. `/mcp` and `/api/owner/<action>` take tokens.
- The upgrade renames the stored resource and managed clients' access to it, and deletes the
  consents, codes and tokens issued for the old name, which no longer verify. It runs once, on
  the first start of 0.16.0.
- API keys still never reach administration, and its key list is still empty.

## Administration over HTTP to access tokens

`POST /api/owner/<action>` serves the administration actions to the same access tokens `/mcp`
takes: `clankerauth:read` lists, and every other action needs `clankerauth:write`. A request
without a token is answered `401` with a challenge naming the resource's discovery; the
dashboard's cookie is not a credential there. The dashboard's own binding, `POST /api/<action>`,
and the issuer's public actions are unchanged. `@clankerauth/admin-api` exports the binding as
`OwnerHttp`.

## The `clankerauth` command

`@gjermundgaraba/clankerauth` is new: `clankerauth login <url>` signs in as the owner through
the browser, as an MCP client does, and every administration action is a command of its own
over `/api/owner`, printing its result as JSON. See the README's "Administer from the command
line". Its first release is published by hand; later ones are published with the other
packages.

## Development package

The development package embeds the 0.16.0 server, so its administration resource is at the
origin root too.
